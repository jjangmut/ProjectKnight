## Goal
Create the **first fresh, independently reproducible baseline of the actual playable ProjectKnight Stage 1** after retirement of historical quality scores. This task is a **measurement and design decision**, not a polish implementation. The acceptable output is genuine Godot windowed gameplay, screenshots/video from that window, input-driven tests, crash evidence, performance measurements and a clear **X/Y vs X/Z gameplay-plane decision**.

The current checked-in design must not be confused with the user's original desired genre:
- Current `CLIENT/Game/project.godot` default main scene is `res://scenes/ui/TitleScreen.tscn`, renderer **GL Compatibility**, viewport **1280×720**.
- `title_screen.gd` routes new campaign to `res://scenes/side_quarter_view/SideQVCampaign.tscn`.
- `SideQVCampaign` loads `SideQVStage1.tscn` as the first of five stages.
- `side_qv_player.gd` is `CharacterBody3D` with advertised **X left/right, Z depth, Y jump**; `side_qv_camera.gd` uses a 3D side-quarter camera and the player is a Sprite3D in a 3D environment.
- The earlier design request for a mobile 2D side-scrolling action game could imply **X/Y side-scroll with no free Z-depth**. The current source does **not** settle whether the discrepancy is intentional. Record as an explicit DESIGN DECISION, never silently convert or declare the existing choice correct.
- Legacy `scenes/stage/Campaign.tscn`, `scenes/quarter_view`, and `scenes/quarter_view_3d` are different variants. **Do not replace the default gameplay route with a legacy or prototype scene** to achieve apparent PASS.

## Gate 2 — input-driven Stage 1 gameplay inspection
Use real keyboard/gamepad/touch input in the running game, not direct function calls, while recording source SHA/time/video or screenshots. Current input map in `project.godot` indicates:
- `A/D` or horizontal arrows: X movement left/right.
- `W/S` or vertical arrows: possible Z-depth movement in current belt-scroll implementation — **measure actual movement, not inferred behavior**.
- `Space`: jump (Y).
- `J`: attack.
- `K`: guard/parry.
- `Shift`: dash (confirm actual assigned key in the running client).

Required test matrix:
A. Idle → left/right run → stop, sprite facing/ground contact and camera follow.
B. Front/back depth movement via W/S; show 3D X/Z position, screen-space delta, occlusion/depth sorting, collision boundaries, visual readability, and whether this conflicts with intended genre.
C. Jump and land, coyote time/jump buffer if observable; distinguish sprite animation from physics Y position. Boundary and pit/cliff interactions.
D. Attack 3-combo, slash/VFX, hitbox, enemy damage and response.
E. Guard, parry timing, dash and recovery; input responsiveness and simultaneous inputs.
F. Enemy AI approach/attack and hit feedback, health loss, death/restart handling.
G. Wave 1 → wave 2 boss spawn, telegraph, boss encounter, victory/failure paths, stage-cleared signal and optional Stage 2 transition. If boss cannot be reached, log where/why; do not fast-forward by calling internal methods.
H. Mobile control overlays: visibility, touch interactions on actual supported test device or explicit PC mouse emulation mode; distinguish mouse emulator from physical touch.
For each action record **Observed / Expected / Result PASS|FAIL|NOT_TESTED / screenshot or video timestamp / error reproduction**. Missing input evidence = NOT_VERIFIED, not PASS. Do not call old smoke-test script output a real interactive playtest.

## Gate 4 — measured PC performance (no synthetic data)
1. Measure real **windowed** Stage 1 at 1280×720, Compatibility renderer. Report GPU/CPU, RAM, OS, VSync, display refresh, full-screen/windowed state, resolution, Godot build and source SHA.
2. Capture FPS / CPU frame time / GPU frame time / draw calls / nodes / memory where available using Godot profiler/monitors; record raw frame/time samples or a Godot profiler export with the method used. Do not invent precision beyond available instrumentation.
3. Measure at minimum: **idle 60 seconds, walking/depth movement 60 seconds, normal combat 60 seconds, boss combat 60 seconds where reachable**. If boss is unreachable, mark missing and open an issue.
4. Report median FPS, minimum and 1% low if frame-level samples exist, p95 frame time, stutter spikes and scene load latency. If only monitor snapshots are available, say so and do not compute fake 1% lows.
5. Reference quality target is **stable 60 FPS** in the specified PC 1280×720 test conditions, but **do not claim Android/mobile FPS** from desktop figures. Actual Android device evidence is separate and may be NOT_TESTED.
6. Existing `STUDIO_V3` Python test or stamina fixture cannot substitute for real game frame-time samples.

## Gate 5 — design decision: fixed X/Y vs belt-scrolling X/Z
Produce `STUDIO_V3/evidence/V3-001/DESIGN_DECISION.md` with a clear table:
- **Option A:** Strict 2D side-scrolling: X left/right + Y jump, no freely controllable Z, side-camera framing. Document compatibility with mobile 4-button intent and costs of converting current 3D stages/enemy AI/collisions.
- **Option B:** Existing 2.5D belt-scroll: X left/right + Z in/out + Y jump; 3D camera, depth lane and occlusion. Document extra mobile input requirements and implications for hitbox, sprite sizing, pathfinding, camera and stage layouts.
- **Option C (only if justified by evidence):** Visually 2.5D rendering with gameplay locked to side-scrolling plane, preserving 3D environment but limiting depth.
For each: gameplay clarity, tactile feel, implementation complexity, existing asset reuse, touch UI, camera, boss encounter, expected rework risks and evidence citations. Include explicit **recommended option and why**, but the **Game Director must explicitly select one**; the Producer and worker cannot silently choose. If Director decision is not returned, `DESIGN_DECISION_PENDING` and V3-001 remains IN_REVIEW/FIX_REQUIRED. No code conversion in V3-001.
