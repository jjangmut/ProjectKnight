## 1. 최우선 산출물 — 실제 플레이 영상 (P0)

- 기존 게임을 **실제 렌더링되는 Godot 게임 창**에서 실행하고 화면을 녹화할 것. Godot 편집기, 테스트 터미널, 설명 슬라이드, 스크린샷 이어붙이기를 플레이 영상으로 대체하지 말 것.
- 가급적 **전체 캠페인 Title 화면 → Deploy → Stage 1 → 2 → 3 → 4 → 5 → 최종 보스 격파 → CAMPAIGN VICTORY → 타이틀 복귀**를 **연속 녹화**할 것. 실제 전투 장면과 게임 입력/적 피격/보스 페이즈 전환이 시청자가 보일 만큼 충분한 플레이 길이를 확보할 것. 기존 자동 E2E는 ~43초로 매우 빠르므로, 가능하면 플레이 관찰용 연출과 실제 조작을 더 느리고 명확하게 보여줄 것. **테스트를 통과시키기 위한 직접 HP 조작, 강제 stage_clear, 타임라인 편집으로 인한 자연 클리어 위장 금지.**
- 화면은 게임 클라이언트의 **1280×720 또는 높은 가로 16:9 해상도**, 30fps 이상 목표; **MP4 / H.264** 권장 (사용자 PC에서 재생 가능). 가능하면 게임 소리 포함, 어렵다면 영상에 `AUDIO_NOT_CAPTURED`를 표시할 것. 검은 화면/프레임 손상/터미널만 나오는 영상 금지.
- 적어도 **Title / Stage1 기본전투 / Stage2 / Stage3 원거리전투 / Stage4 골렘 / Stage5 최종보스의 두 페이즈 / 캠페인 승리 화면**이 육안으로 확인되는 구간을 포함할 것.
- 가능하면 실제 키보드/마우스로 사람이 직접 플레이한 연속 영상이 최선. 실제로 에이전트가 `InputEvent`를 주입해 자동 플레이한 영상이면 **`AUTOMATED_ENGINE_INPUT_PLAYTHROUGH`** 라고 영상 설명과 보고서에 명시할 것. 사람 플레이로 위장 금지.
- 자동 플레이 E2E를 촬영하려면 실제 Godot 윈도우 게임 클라이언트 전체가 그려진 상태를 OS 화면 캡처로 수집할 것. 기존 5개 스테이지 E2E fixtures (`CLIENT/Game/tests/v3_015_campaign_smoke.gd` 등) 재사용 가능. **진짜 Godot 프레임을 캡처**한다면 자동 입력 영상도 가치가 있다.
- 녹화 방식은 Windows Game Bar, OBS (설치되어 있다면), 또는 설치된 ffmpeg 화면 캡처 등. 기존 컴퓨터에 도구가 없으면 신뢰 가능한 경로로 준비하되 불필요한 설치/보안 기능 해제 금지. 녹화는 게임 창만 대상으로 하고 다른 창, 사생활 정보, 토큰, 사용자 문서가 보이지 않게 할 것.

## 2. 사용자에게 실제로 재생 가능하게 전달 (P0)

- 파일 생성 성공을 메타데이터가 아닌 **실제 영상 파일**로 검증할 것: 파일 존재, 크기, `ffprobe` 또는 동등 도구로 컨테이너·코덱·해상도·fps·재생시간 확인; 앞/중간/끝 프레임을 디코딩해 **검은 화면·정지 화면 여부** 점검.
- 영상 길이가 너무 길면 **시청용 하이라이트 MP4 2~5분** 추가 제작 가능. 다만 원본 연속 촬영분을 반드시 별도로 보존하고, 컷 편집한 하이라이트는 `HIGHLIGHT_EDITED`라고 명시할 것. 자동 플레이 길이가 실제로 더 짧으면 없는 분량을 늘리거나 속도를 조작하지 말고 실제 길이를 그대로 보고.
- 사용자 Windows PC의 안정적인 경로에 저장. 권장:
  `D:\JUNYPAPA_STUDIO\Videos\ProjectKnight\V3-020\ProjectKnight_Playtest_Full.mp4`
  `D:\JUNYPAPA_STUDIO\Videos\ProjectKnight\V3-020\ProjectKnight_Playtest_Highlights.mp4` (선택)
- 결과 보고서에 **실제 로컬 절대경로**, 크기, 재생시간, 해상도, 오디오 포함 여부를 제공. GitHub 소스 저장소에 수백MB 영상 무단 커밋하지 말 것. 업로드가 필요하면 사용자가 명시적으로 승인한 위치만 사용. 사용자가 영상 파일을 이 채팅에 직접 첨부하면 ChatGPT가 재생 화면을 분석할 수 있도록 **업로드할 파일명과 경로**를 명확히 알릴 것. GitHub Markdown 내 `file:///D:/...` 링크를 외부에서 재생 가능한 링크로 잘못 소개하지 말 것.
- 동영상 재생을 실제로 확인할 수 없으면 `VIDEO_NOT_VERIFIED`로 보고하고 완료라고 말하지 말 것.

## 3. 검증·범위 제한

- 새 스테이지/기능 구현, Android 기기 테스트, APK 최적화, 자동화 런처 개발, 예전 QA 검증 반복 **불필요**. 이 작업은 영상 촬영과 사용자 전달이 핵심.
- 실행시 Godot 창과 E2E 입력 테스트의 실제 관계(사람 플레이인지 자동화된 engine-input인지) 명시. 게임을 강제로 클리어시키는 치트나 상태변조 금지. Option C Z=0 전투 평면/5개 스테이지 유지.
- 변경은 `STUDIO_V3/evidence/V3-020/`의 짧은 `VIDEO_REPORT.md`, `VIDEO_METADATA.json`, 필요 시 작은 전용 녹화 스크립트/테스트만. **이미 진행 중인 다른 게임 개발 브랜치 및 원본 워크트리 보호**. 메인 개발 Worktree를 체크아웃하거나 수정하지 말 것.
- 원본과 하이라이트 재생 점검 및 검증결과 기록 후 evidence만 커밋하고 원격 Push. 게임 코드에 손대지 않은 작업이면 게임 코드 변경을 꾸며낼 필요 없음. QA는 실제 녹화 증거와 설명의 진실성을 확인하고, 수행하지 않은 Android 테스트를 PASS로 쓰지 말 것.
