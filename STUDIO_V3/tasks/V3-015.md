**Engine:** Godot 4.7.2 Compatibility, landscape 1280x720 and 1024x720, intended mobile target.

## Goal — shift from UI/control plumbing to visible game quality
After V3-010–014 established controls, audio, encounter feedback, defeat/retry, and stage-clear intermission, **improve actual rendered in-game visuals**. Screenshots and tangible in-game code/assets matter more than an inflated report score. No infrastructure rewrite or repetitive old QA bureaucracy.

## A. Audit actual rendered experience (bounded)
1. Launch actual playable Stage 1, Stage 3, Stage 4 and Stage 5 (at least one gameplay frame per stage, including combat where possible). Collect 1280x720 real screen captures. Inspect backgrounds, palette, scene depth, character silhouette, foreground occlusion, enemy/attack readability, UI safe areas and scene transitions. Do **not** fabricate quality problems from names or comments.
2. Record the top 3 **visible** shortcomings ranked by player impact, citing precise files/scenes and visual before evidence. Examples to evaluate, not assume: monotonous ground/backdrop, low character-background separation, floating props, competing visual effects, HUD overlays obscuring combat.
3. Keep a small timeboxed scope, prioritize Stage 1 plus one later-stage contrast improvement with reuse where practical; don't redo all five stages cosmetically at once.

## B. Make real graphic changes
- Deliver **at least two clearly visible improvements** to world/background/lighting/composition plus **one targeted combat readability/FX visual improvement**, implemented in actual scene/GDScript/material/texture assets. Prefer reusable small modules or existing level constructs.
- Preserve existing art style and performance targets. No unsourced copyrighted imagery. For new assets document provenance and ensure project files commit. Avoid shader features incompatible with Compatibility renderer and avoid high fill-rate overdraw on mobile.
- Maintain clear player/enemy silhouettes under all attacks and boss telegraphs, consistent Z=0 actor plane, readable touch controls and rewards, stages 1–5 intact.
- **Bounded correctness fix:** inspect `side_qv_campaign.gd::_show_stage_clear_intermission()`: V3-014 code falls back to a second hardcoded `shard_rewards` map and default 20 when `last_earned_shards` is unavailable. This conflicts with V3-014's intended single-source reward UI. Remove speculative fallback; read authoritative stage reward or explicitly show “reward unavailable” without inventing a number. Do not re-award or change actual shard values. Add one focused negative-path assertion.
- Inspect any concrete game-facing risks exposed by the visual changes; avoid unrelated infrastructure.

## C. Tests and evidence
- Collect paired **real Godot rendered** before/after 1280x720 captures for the changed scenes, plus a 1024x720 gameplay layout audit; contrast actual pixel changes and explain why gameplay readability improved. Do not count screenshots merely asserting a score as visual proof. Include one short GIF/video only if easily recorded without importing new systems.
- Measure FPS/frame time under a reproducible representative enemy/boss combat scene **before and after** where possible, under same hardware/scene conditions; report both numbers, no fabricated 60FPS gate. Check excessive new draw calls, overdraw or leaked nodes when using particles/shaders.
- Focused visual source checks and actual scene load, then V3-012 combat-readability, V3-011 audio, V3-010 touch regression, V3-013 defeat/retry and V3-014 stage-clear flow; continuous 5-stage Title -> Victory -> Title -> second run with Continue clicks. Retain 0 Z-plane violations.
- Put raw command/stdout/stderr/exit and actual rendered captures in `STUDIO_V3/evidence/V3-015/`. Mark Android hardware, human feel and subjective visual assessment NOT_VERIFIED if not done. No synthetic PASS or proxy image replacing game rendering.

## D. Completion
- Freeze meaningful game **code/assets** and evidence in a commit before independent PK_QALead / PK_GameDirector review on that same SHA. Commit review and STATE separately; push branch with full actual SHAs.
- State changed files, exact player-visible differences, pre/post performance evidence, open visual defects, and unresolved limitations. Don't claim commercial release readiness.

**Order:** play/render inspect -> choose top problems -> implement visual/game changes -> rendered comparison/performance -> focused regression -> freeze/review/push.
