## 1. P0 — Replace overly large red rectangular danger telegraphs

- Reproduce original issue around Encounter 2/3 in recorded V3-024-R4 gameplay and inspect enemy and stage code to identify **which specific node/material produces the broad red rectangle**; do not edit arbitrary VFX without reproduction.
- Replace flat opaque area(s) with **shape-accurate, textured, readable** attacks in actual game: crossbow uses narrow directional line/beam with clear windup-to-fire; shield/cleave uses appropriate arc/cone; quake uses ground ring, each matching damage collision geometry. Red is not prohibited but an oversized unshaded blanket is unacceptable.
- Each telegraph has distinguishable phases: anticipation `TELL`, dangerous `ACTIVE`, and `RECOVERY`. The high-intensity cue precedes damage, doesn't cover player/enemy silhouette, is visible from actual 1280×720 camera, and fades promptly after attack. Respect legibility for color-blind users (shape/animation, not color alone).
- Attack warning **shape must match effective X/Z damage zone**. Record cue start/end frames and hitbox activation and actual hits/misses. A preview VFX in isolation is not sufficient.
- Be mindful of Godot Compatibility materials and overdraw. Measure 60FPS performance on available Windows build; no unsupported Android performance PASS.

## 2. P0 — Make enemy roles produce distinct player decisions

Keep three Stage 1 encounters and preserve existing narrative/zone architecture; tune actual enemy behaviors and staging:
1. **Encounter 1 / melee grunts:** Teach directional spacing, committed attack with recovery, obvious vulnerability after a whiff. Player can counter instead of spamming.
2. **Encounter 2 / crossbow:** Force an understandable choice between Z sidestep, dodge timing, closing distance or guard/parry; crossbow aim line should trace origin correctly and bolt should match it. Respect projectile vanish/reflect regression.
3. **Encounter 3 / shield knight:** Visually and mechanically require facing/flank or punish after shield bash. Front spamming gets blocked without an indefinite stalemate. No unavoidable enemy collision squeeze or overlap.

- Use authored behaviors, attack roles, patrol/spacing and fair tells. Avoid arbitrary enemy HP inflation or more mobs for its own sake. Tune effective enemy engagement windows, recovery, movement speed, simultaneous attackers and walk/dash distance; preserve an escape route.
- Maintain a decision ledger: which action created tactical opportunity, against which AI pattern, player-visible cue, resulting recovery, damage taken, parry/flank counts, and clear time.
- Protect previous boss lane/corner fixes: classic left/right sprite during Z traversal; boss/hero same footline when exchanging melee, Z dodge works, camera includes both actors, no sprite overlap. **Do not reopen camera systems without measured regression evidence.**

## 3. P0 — Human-playable local test flow

- Create a **normal launch path**, not a test fixture, for human Windows keyboard/gamepad (if already mapped). In-game start/retry/pause, clear control instructions visible in game, death/restart works, access Stage1 directly from existing campaign/menu without developer console.
- Test with actual human operator when available; log qualitative feedback from at least two genuine attempts per person (first encounter, ranged cue, shield flank, boss, camera visibility, controls and difficulty). If no operator: implement instrumentation and provide **an explicit short test checklist**, mark `HUMAN_PLAYTEST_NOT_TESTED`, no fake survey or human approval.
- Non-invasive debug mode only: optional overlay shows input state and encounter times, HP, parry, dash, cue-response latency; disabled in release footage, no game-state modifications. Keep mobile controls intact.

## 4. P1 — Pacing and fairness, not fabricated duration

Run **same-build, same-source, identical seed or logged seed**, at least four policies: stationary attack-only, forward+attack spam, X/Z attack no defense, tactical play. Additionally baseline two script reaction latencies (e.g. 250ms and 450ms) so bot's frame-perfect parries do not become a proxy for human skill. Log action success (successful parry/dash/guard), effective enemy attack cycles, enemy misses/hits, encounter durations, idle traversal, total time, deaths, healing pickups and retry.

- Do not make all bots win. Forward spam should usually suffer more than tactical policy in meaningful scenarios. Favor fight clarity and counterplay, not forced duration.
- Check high-frequency parry automation: previously V3-024-R4 report counted 53 parries in 35.63 sec. Investigate whether `parries_performed` means **true timed successful parries** or merely guard inputs; distinguish counters, attempts and confirmed enemy attacks. Overcounted instrumentation must be corrected.
- Do **not** claim 2–4 minutes achieved if not supported by actual human runs. Track clock honestly in 1x media and UI.
