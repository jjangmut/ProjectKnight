## 1. P0: honest multi-layer test system

Create a **small in-repo Godot 4.7.2 gameplay verification kit**, e.g. `CLIENT/Game/tests/quality_gate/` with scripts and README plus one simple Windows CLI entry script if useful. Avoid huge orchestrator/app/agent hierarchy. Three separate **noninterchangeable** result categories:

**A. Mechanics tests (deterministic isolated):** direct placement/state setup is allowed **only in designated fixtures** and labeled `ISOLATED_FIXTURE`; directional damage hit vs miss, knockback and attack/VFX spatial origin, full 8-way X/Z movement, collision/depth rails, guard/parry hit windows, enemy telegraph timings, boss attack recoverability, checkpoint/retry. Each test emits input setup, observed result, expected result, source SHA, game version and PASS/FAIL. Never use fixture evidence as natural gameplay.

**B. Natural no-cheat gameplay E2E:** controller may send action input, read frame transforms/event notifications and write telemetry, but **never modify game actor state or call damage/spawn/kill/AI pattern functions**. Static allowlist and runtime input trace. Run multiple deterministic **behavior policies on the same production gameplay**:
1) standstill attack-only (diagnostic, not anti-spam acceptance),
2) **forward-move + attack-only**: cannot use guard, dash, jump, or Z; measure survival/progress/damage, crucial baseline,
3) move X/Z + attack, **no guard or dash**,
4) full combat policy X/Z + attack + guard/parry/dash/jump,
5) idle defensive/no attack or other pathological case if helpful.
Each logs time, positions, unique enemy IDs/roles, actual damage, parries that CONNECT vs button presses, actual invulnerable dash dodges, boss patterns that genuinely ACTIVE and damaged/missed, attack collisions/whiffs, health pickups, stage clear/death/retries, cause of failure and random seed. Repeat a few seeds, summarize outcomes rather than one scripted ideal run. Do not hardcode an automatic failure criterion that always passes with movement gate; test boss in combat **after normal level progression** and compare proper policies fairly. If a policy unexpectedly wins, report it honestly as balancing defect; do not mutate HP to rig outcomes.

**C. Visual/UX frame review (actual Godot render):** capture true rendered image/video synced to event log time/frame via frame index. At minimum one visual batch for each cardinal attack X+/X-/Z+/Z-, diagonals, enemy frontal shield + back hit, telegraphed crossbow shot, each 3 boss attacks (startup, active, recovery), contact VFX hitbox timing, X/Z traversal and scrolling, damage/HP/retry, stage clear. Generate 1280x720 images with unclipped UI and automated contact sheet. The tool **must not mark visual alignment or fun as PASS based solely on code**. Record objective overlay or offline annotations showing true attack hitbox and directional arc at same frame (QA/debug overlay may be optional test mode, never gameplay cheat); systematic visual comparison with reviewer severity and reproducible timestamps. Include 1) camera/actor visible frame occupancy, 2) feet/shadow X/Z alignment, 3) sprite front/back facing from player perspective, 4) telegraph contrast/legibility, 5) boss and small enemies foreground occlusion, 6) UI touch occlusion. Output `VISUAL_REVIEW_PENDING` until a human watches actual captured frames. No arbitrary AI quality score or fictitious screenshots.

## 2. P0: fix evidenced player-facing defects, not just tests

After generating failing tests/screens/video, fix top blockers:
- Attack animation frame vs slash VFX vs physical hit at all X/Z directions; proper facing for depth up/down (billboard sprite flip is **not** four-directional animation). If source animation lacks front/back rows, use truthful temporary silhouettes and record asset requirements. Do not claim 8-way polish without sprites.
- Stage has to feel scrollable: traversal camera movement, enemy distribution, gates, hazard anticipation and pace. Run 1–2 minute natural trials; **target** first-time human Stage1 2–4 min, but no fake stopwatch sleeps, no increasing HP purely to pad time. A fast expert run may be shorter; human results rule.
- Boss patterns must be readable/counterable in rendered frames, not only `current_pattern` enum available to test bot; verify warning time in milliseconds and signal/visible frame sync.
- Enemy AI must land some attacks against real reasonable inputs but not be unfair. Shield can be countered with real depth flank, AI retaliation occurs, ranged attacks not free kills.
- Move+attack spam comparison should genuinely produce inferior results to varied defense; avoid counting inability to reach boss as an anti-spam proof.
