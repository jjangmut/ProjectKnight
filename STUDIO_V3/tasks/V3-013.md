## Why this task
Real source `CLIENT/Game/scripts/side_quarter_view/side_qv_campaign.gd` currently handles `_on_stage_failed()` by printing a log, waiting two seconds, and **automatically reloading the same stage**. The player cannot choose retry vs title, cannot inspect defeat feedback, and a deferred timer may outlive a transition. The final victory panel already has usable Replay and Return-to-Title button patterns. Improve the **actual loss/retry loop**, not infrastructure, more test harnesses or ceremonial documents.

## Checkpoint A — inspect game flow, then implement
Inspect `side_qv_campaign.gd`, `side_qv_stage_base.gd`, existing stage_failed emission, player death, title scene and virtual controls. Confirm how failure is triggered, whether input remains active, and whether a dead scene can still fire boss/stage events. Record current reproducible player-facing behavior with one real rendered before capture.

Implement a coherent stage defeat experience:
1. When the player dies, show a readable **Stage Failed** overlay with stage name/number and clearly tappable **Retry Stage** and **Return to Title** actions. Use existing CampaignUILayer and style conventions; no assets needed. Support desktop mouse and mobile touch, keyboard/gamepad focus where already supported. Properly anchor/center at 1280x720 and 1024x720, no clipped controls.
2. Freeze or block **combat input and enemy damage** appropriately while defeat overlay is active without pausing UI input or leaving stuck virtual actions. Prefer a minimal stage-local gating/cleanup mechanism based on existing player/controls methods, not global pause unless its full semantics are verified.
3. Clicking Retry should create a **fresh instance of the failed stage exactly once** and clean up previous UI/stage/audio/virtual input. Clicking Title must return to the existing title scene via the established navigation/audio reset path. Guard duplicate taps, duplicate `stage_failed`, stale `await`/timers, and failure-victory races. No unintended double-stage instantiation.
4. Preserve all earlier completed stages' progression status as appropriate to retrying the current stage; no accidental next-stage advancement or reset of unrelated progression. Do not introduce checkpoints/saving, new damage balance, or unrelated redesign.
5. A short defeat feedback sound may be added only if justified and compatible with existing V3-011 AudioManager; prioritize playable flow first. Do not repeat audio infrastructure verification beyond the regression.
