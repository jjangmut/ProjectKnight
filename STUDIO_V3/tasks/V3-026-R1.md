During normal attacks, the new 3D-derived Paladin sprite looks **broken/deformed/fragmented** and worse than the preexisting character. The intended game art is 2D side-facing sprite sheets for a 2.5D belt-scroll game. **No broken 3D-looking models should appear during attacks in the release gameplay path.**

The actual problematic new assets are confirmed runtime-bound in `side_qv_player.gd`:
- `TexCombo1 = res://assets/player_frames/combo1_slash.png` (3x2)
- `TexCombo2 = res://assets/player_frames/combo2_slash.png` (3x2)
- `TexCombo3 = res://assets/player_frames/combo3_cleave.png` (4x2)
and rendered via `tools/combat_animation_pipeline/render_combat_combos.py` from `ProjectKnight_Paladin_Animated.glb`.

**IMPORTANT verified source problems to investigate, not assert as proven visual root cause until inspecting actual PNG frames**:
1. Blender pipeline line ~188–207 forcibly sets every imported pose bone `rotation_mode='XYZ'; rotation_euler=(0,0,0)`, then assigns independently made Euler triples directly to specific bones. This is hand-authored procedural pose hacking of an imported rig, **not playback of validated source animation actions** and does not establish bone rest basis, armature skinning constraints, proper hand-to-sword attachments or real keyframe motion. Strong candidate for unnatural/broken geometry.
2. It describes arm/torso poses as if Blender world-axis Euler corresponded to anatomical local axes; per-bone orientation may differ. Combo3 includes severe Hips/Chest/leg rotations. Need inspect armature rest matrices, weight maps, skinning, negative scales, object transform and bind pose.
3. Script line ~284 calls `cell.paste(im,(shift_x,shift_y),im)` where source RGBA already contains alpha; PIL can effectively alpha blend again into an initially transparent RGBA cell. Compare raw alpha histogram/edges versus a single-copy direct composite/paste; avoid double-alpha halos and background darkening. This may explain artifacts but does not independently prove fractured body geometry.
4. Atlas is auto-aligned using the **entire nontransparent bounding box**, then places its bottom at foot pivot `y=700`: if sword or flare extends below feet, computed bottom is not the actual planted foot. This creates per-frame sliding, jumping and wrong pivots. Use rig-defined persistent projected ground socket, not min/max alpha bounding.
5. The generated PNG files are actually committed and referenced by runtime. A passing file existence check, build, deterministic hit timing or bot victory **is not a visual-quality PASS**.
