## Mission
Make the **single Producer entrypoint** actually run the worker, QA reject, a new worker repair, QA retest and Director review. Every role's verdict must come from an independently verifiable runtime invocation, not from a user-provided role string or the fact that a process exited.

Previous R1 progress: five separate native-subagent transcripts and a fixture repair exist. These show multi-agent activity, but NOT that the Python TaskDispatcher managed the sequence, nor that approval identity and reviewer verdicts are secure. Treat past reports as evidence to examine, not an approval.

## Phase 1 — Trusted invocation registry (P0)
Create a provider-attested invocation record, stored by the dispatcher *at launch/completion*, not accepted from untrusted CLI parameters. Minimum fields:
`run_id, task_id, iteration, role, provider, invocation_id, session_id, worktree, branch, target_commit_sha, started_at, completed_at, terminal_status, result_hash`.
- Distinguish `operator_manual`, `mock`, `provider_live`. Operator and mock never satisfy the AI-review gate.
- Bind review to exactly one registered role, one fresh session and one exact submitted SHA. Check worker/reviewer separation and two independent reviewer sessions.
- Do not count role strings as identities; when provider cannot attest roles/sessions, report `IDENTITY_NOT_VERIFIED`.
- Use source of truth in SQLite with unique keys; reject a reused invocation/session or mismatched role/commit/iteration. Keep a separate explicitly named manual operator review route that cannot assert independent AI approval.
- Never fabricate provider metadata.

## Phase 2 — Structured review semantics (P0)
`SUCCEEDED` means agent execution completed; it does NOT mean a review passed.
Require a structured reviewer result:
```json
{"task_id":"...","iteration":2,"role":"PK_QALead","reviewed_commit_sha":"<40-char SHA>","verdict":"PASS|FIX_REQUIRED","issues":[{"severity":"P1","title":"...","steps":"...","expected":"...","actual":"...","evidence":["..."]}],"evidence_manifest":"..."}
```
- Parse and validate result schema; ensure issue ownership and evidence. `FIX_REQUIRED` routes to issue creation and fix queue, even if the process status is SUCCEEDED.
- A missing/malformed/conflicting verdict, unknown/unverified status, empty evidence, or stale SHA must fail closed (`NOT_VERIFIED` or `FIX_REQUIRED`), never default PASS.
- Verify user-facing work proof is committed, content hashes match, and review targets the commit that produced those artifacts.

## Phase 3 — Actual integrated runtime (P0)
- Implement exactly one supported command/IDE action that dispatches the full fixture in the correct sequence. Prefer Antigravity native IDE subagents when available; investigate actual official handoff/return channels and record them. Use stand-alone `agy` only if truly installed and verified. A call to AgentAPI `new-conversation` is NOT a finished worker.
- Connect runtime invocation record → verified terminal output → task evidence → independent QA review → issue → rework → QA retest → Director.
- In `dispatcher.py`, `worker_action` and `reviewer_evaluators` must be explicit **mock-test-only** options, rejected in production mode. Do not pass a local Python callback to simulate real independent QA in production.
- The configured runtime must either truly execute the chain or truthfully stop as `LIVE_AUTONOMOUS_LOOP_NOT_VERIFIED`, with no false approval.
- Capture both the executed adapter call chain and the corresponding event-log/state-machine transitions in one correlated `run_id`. A pile of manually launched sessions is insufficient.

## Phase 4 — Concurrency and Git provenance (P1)
- Replace actor-name leases with unique `run_id` claim tokens; prevent two Producer processes with the same role label from claiming one task simultaneously. Claim only after validating status, dependencies and branch, or ensure unconditional rollback on errors.
- Use atomic expected-version state transitions and immutable event IDs; avoid task lock leaks after a failed start.
- Lock write access per Git worktree/branch; enforce protected branch safety in real dispatch.
- Confirm that the worker-submitted Git SHA actually exists, belongs to the designated worktree/branch and contains reviewed changes. `git rev-parse HEAD` from the caller's unrelated checkout is insufficient.
- Add two-process competition and crash/recovery tests.

## Phase 5 — Single-entry live proof (required)
Operate only on a throwaway fixture, never actual game systems:
1. Producer invokes Worker A via actual supported runtime. Worker commits a small intentionally flawed component.
2. Independent QA is dispatched from the SAME run, detects a P1 and returns explicit `FIX_REQUIRED`; issue is persisted with evidence.
3. Producer invokes Worker B in a new iteration and isolated writable context. Worker commits a concrete fix.
4. Independently dispatched QA retests the *new exact SHA*, issues `PASS` and records issue resolution after verification.
5. Independently dispatched Director checks the exact same SHA, returns explicit PASS, and the two-key gate approves **fixture task only**.
6. Save `run_id`, per-role provider/session IDs, verified completion envelopes, repo SHA, task JSON before/after, SQLite event log, state changes, executable test logs and artifact checksums.
7. Include one live negative test: a reviewer finishes successfully but says `FIX_REQUIRED`; gate must reject.

If the native IDE interface cannot be called by the Python process, implement a documented IDE-host bridge if officially supported; otherwise use operator-mediated dispatch **and label it non-autonomous**, retaining V3-002 as FIX_REQUIRED. Never invent undocumented private endpoints.
