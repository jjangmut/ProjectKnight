## Phase 1 — make one PK_Producer entrypoint (P0)
Implement a practical **Producer procedure in native Antigravity**; place it where Antigravity can actually discover/invoke it (verify its native format before writing), e.g. `.agents/agents/PK_Producer.md` plus `STUDIO_V3/docs/NATIVE_PRODUCER_RUNBOOK.md`.

From one user instruction the Producer must:
- create a unique run ID, claim a single task, load task acceptance criteria;
- invoke the worker through the actual native IDE tool and receive terminal outcome;
- submit worker-generated commit/evidence to the Python control plane;
- invoke a different QA session; parse explicit `PASS` or `FIX_REQUIRED`;
- create P0/P1 issue on QA rejection, dispatch a fresh worker iteration to fix it;
- invoke a new QA session for retest, then a separate Director session for the exact same SHA;
- leave truthful final task status, audit log, and a ready next action.

## Phase 2 — provenance / anti-replay gates (P0)
1. Bind `run_id + task_id + iteration + agent role + parent conversation + provider session + exact target Git SHA` at dispatch time, not only at report ingestion.
2. Validate provider session's actual subagent `typeName`, parent conversation, result completion event, task/iteration/commit and target SHA; do not accept arbitrary caller-supplied target SHA as proof.
3. Replace `INSERT OR REPLACE` in trusted invocation registry with immutable insert / explicit controlled terminal update. Duplicate or reused session IDs and invocation IDs must fail; never silently overwrite provenance.
4. A transcript containing some earlier `status:DONE` event is not proof that the latest whole subagent job completed. Require the documented final terminal marker and validated result schema; otherwise `COMPLETION_NOT_VERIFIED`.
5. New untrusted prompts/reports must not be able to mark QA PASSED merely by writing string labels to a file.

## Phase 3 — protect real approval from test mode (P0)
- The live two-key gate requires two distinct **provider-verified** QA + Director invocations tied to the submitted SHA.
- Existing `allow_mock=True` defaults in `policies.py` and the provider label mismatch (actual `MOCK_SIMULATED`) must be fixed. MOCK and OPERATOR_CLI never satisfy a production milestone.
- Test mode outputs `SIMULATED_APPROVAL`, never production `APPROVED`. Use a separate disposable queue or explicit safety context.
- `SUCCEEDED` means execution completed; reviewer verdict is separately parsed and may be `FIX_REQUIRED`. Missing, malformed, fabricated or stale verdict fails closed.
- Worker's actual submitted SHA must be verified from the worker's isolated Git worktree/branch; evidence content and review must match that immutable revision. The latest checkout HEAD in Producer's repository is not sufficient.
- Fixture approval is **not** the same as V3-002/R3 infrastructure approval. Evaluate the latter against the current code HEAD separately.

## Mandatory regressions
- Two forged CLI approvals with arbitrary sessions -> denied.
- Actual `MOCK_SIMULATED` provider never causes live approval.
- Duplicate/reused verified session across tasks/commits -> denied.
- Wrong parent conversation / wrong task / wrong SHA -> denied.
- Partial transcript DONE with final task not done -> denied.
- SUCCEEDED + FIX_REQUIRED -> issue, not PASS.
- SUCCEEDED + missing structured verdict -> blocked.
- Approval clears lease.
- SHA not on assigned branch, uncommitted evidence, stale artifacts -> rejected.
- Two concurrent Producer claims + interruption/retry do not duplicate writes.
- Existing tests remain green. Commit reproducible Python and Godot fixture tests and **raw** outputs (not narrative-only).
- Native bridge with zero bound sessions does not claim a successful dispatch.
