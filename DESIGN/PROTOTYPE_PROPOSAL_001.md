## 1. 기획 리드 의견

### 핵심 플레이 경험

플레이어는 적의 예고 동작과 지형 위험을 보고 공격할지, 위치를 바꿀지, 회피할지 판단한다. 공격에는 짧은 빈틈이 있어 무작정 연타하기보다 안전한 순간을 선택해야 한다.

긴장감은 제한된 체력과 연속되는 위협에서 나오고, 성취감은 패턴을 학습해 이전보다 적은 피해로 구간을 돌파하는 데서 나온다. 핵심 재미는 높은 처벌 자체가 아니라 **위험을 읽고 의도한 조작으로 극복했다는 감각**이다.

핵심 경험의 순서는 **위협 관찰 → 행동 판단 → 짧은 실행과 피드백 → 패턴 학습 → 더 안정적인 돌파**다.

### 핵심 플레이 루프

1. 안전한 시작 구간에서 이동·점프·공격 확인
2. 일반 적과 단순 지형 위험 조우
3. 서로 다른 패턴의 적을 조합한 전투
4. 중간 체크포인트와 일시적 공격 강화
5. 강한 적을 통해 학습 내용 재확인
6. 2~3개 패턴을 가진 보스
7. 클리어 결과와 재도전 선택

튜토리얼 팝업을 연속으로 보여주기보다 첫 구간의 배치와 시각적 신호로 기본 조작을 익히게 한다.

### 모바일 조작 후보

| 항목 | 안 A — 수평 이동 영역 + 3개 행동 버튼 | 안 B — 좌우 버튼 + 공격 자동화 |
|---|---|---|
| 구성 | 왼쪽 드래그로 좌우 이동, 오른쪽 공격·점프·회피 | 왼쪽 좌우 버튼, 오른쪽 점프·회피, 유효 거리에서 자동 공격 |
| 터치 정밀도 | 이동 영역이 넓고 행동이 명시적이라 원인과 결과가 분명함 | 이동은 명확하지만 자동 공격 시점이 의도와 다를 수 있음 |
| 화면 가림 | 오른쪽 버튼 3개의 크기와 간격 조정 필요 | 버튼 수가 적어 화면 가림이 작음 |
| 고전 액션 긴장감 | 공격 시점을 직접 선택해 판단과 실행이 유지됨 | 접근성은 높지만 공격 타이밍 숙련이 약해짐 |
| 모바일 접근성 | 버튼 수는 많지만 기능 대응이 직접적임 | 진입은 쉽지만 자동 공격 규칙을 이해해야 함 |

**기획 권고:** 안 A를 우선 사용한다. 공격을 포함한 조작감이 재미있는지 검증해야 하므로 공격 시점을 자동화하지 않는다. 버튼 위치·크기·입력 유예는 기기 테스트로 조정한다.

### 난이도 방향

고난도 고전 액션과 현대 모바일 액션의 중간을 권고한다.

- 적 공격은 짧지만 식별 가능한 예고 동작을 가진다.
- 플레이어는 기본적으로 3회 피격까지 허용한다.
- 일반 공격은 즉사시키지 않는다.
- 중간 체크포인트 1개를 두고 실패 시 빠르게 재시작한다.
- 잔기, 장기 진행 손실, 반복 파밍은 사용하지 않는다.
- 보스는 2~3개 패턴을 명확히 구분하고 조합한다.

프로토타입은 “어렵지만 이유를 이해할 수 있고 바로 다시 시도할 수 있는가”를 확인한다. 최종 난이도는 확정하지 않는다.

### 프로토타입 범위 검토

| 후보 | 판단 | 이유 |
|---|---|---|
| 플레이어 1종 | 포함 | 이동·점프·공격·회피 검증의 기준점 |
| 기본 공격 | 포함 | 핵심 판단과 타격감 검증 |
| 점프 | 포함 | 횡스크롤 공간 판단과 지형 대응 검증 |
| 회피 | 포함 | 모바일에서 위험 대응이 공정한지 검증 |
| 무기 1~2종 | 축소 포함 | 기본 무기 1종과 일시적 공격 강화 1종만 사용 |
| 일반 적 | 포함 | 행동이 다른 2종으로 조합 전투 검증 |
| 강한 적 | 포함 | 일반 적 1종의 강화형으로 제작비 절감 |
| 간단한 보스 | 포함 | 조작과 패턴 읽기의 종합 검증 |
| 스테이지 1개 | 포함 | 5~10분의 단일 선형 구간 |
| 체크포인트 | 포함 | 재도전 피로도 검증을 위한 중간 지점 1개 |

## 2. 아트 리드 의견

### 표현 방식 후보

| 기준 | 2D 픽셀 아트 | 2D 고해상도 일러스트 / 스프라이트 | 2.5D |
|---|---|---|---|
| 제작 비용 | 작은 해상도는 유리하나 정교한 픽셀 애니메이션은 별도 숙련 필요 | 제한 프레임과 파츠 재사용 시 관리 가능 | 모델·리깅·조명 구축으로 가장 높음 |
| 애니메이션 | 프레임을 줄일 수 있으나 수정이 수작업 중심 | 파츠 분리와 제한 애니메이션으로 반복 제작 가능 | 리깅 후 재사용 가능하지만 초기 비용이 큼 |
| 적 확장 | 팔레트·실루엣 변형에 유리 | 공통 골격과 파츠 규격으로 확장 가능 | 현 단계에는 과한 기반 작업 필요 |
| 모바일 성능 | 유리 | 텍스처와 오버드로우 관리 시 적합 | 조명·셰이더·모델 복잡도 관리 필요 |
| 가독성 | 작은 화면에서 실루엣 관리가 쉬움 | 명암과 외곽선을 직접 통제하기 좋음 | 원근과 조명이 가독성을 방해할 수 있음 |
| 생성형 AI | 콘셉트 보조 가능, 픽셀·프레임 일관성 보정 필요 | 콘셉트와 원화 초안 활용 가능, 애니메이션 일관성 보정 필요 | 생성 후 정리·리깅 비용이 남음 |
| 차별화 | 단순 복고 게임으로 보일 위험 | 고유 실루엣과 색 설계로 원작과 거리 확보 가능 | 표현 폭은 넓지만 프로토타입에 과투자 |

**아트 권고:** 제한된 애니메이션을 사용하는 2D 고해상도 스프라이트를 우선한다. 픽셀 아트는 제작비가 반드시 낮지 않고 복고 복제로 보일 위험이 있으며, 2.5D는 첫 프로토타입에 과하다.

### 프로토타입 아트 범위

- 색과 실루엣이 구분되는 단순 임시 스프라이트를 사용한다.
- 플레이어는 대기, 이동, 점프, 공격, 회피, 피격 상태만 구분한다.
- 일반 적 2종은 실루엣과 공격 예고 색을 다르게 한다.
- 강화형 적은 기존 적의 크기·색·효과를 변형해 재사용한다.
- 보스는 2~3개 공격 패턴의 예고 동작에 우선 투자한다.
- 배경 장식보다 플레이 영역과 충돌 지형의 가독성을 우선한다.
- 타격 효과, 피격 점멸, 위험 예고는 임시 Asset이라도 제공한다.

최종 캐릭터 원화, 세부 배경, 다량의 애니메이션과 시네마틱은 제외한다. 생성형 AI는 콘셉트 탐색과 참고 시안에만 사용한다.

### IP 차별화

- 원작을 연상시키는 갑옷, 해골·묘지 배치, 무기 실루엣과 색 조합을 묶어서 재현하지 않는다.
- 캐릭터 비율, 이동 자세, 공격 궤적, 적의 실루엣 언어를 독자적으로 설계한다.
- 표면적인 복고 기호보다 가독성 높은 형태와 고유한 움직임 원칙을 먼저 세운다.
- 세계관과 캐릭터는 확정하지 않고 중립적인 임시 모티프를 사용한다.

## 3. 클라이언트 리드 의견

### 시스템별 구현 난이도

| 시스템 | 난이도 | 주요 검토점 |
|---|---|---|
| 이동 | 중 | 가속·감속, 공중 제어, 단순 수평 지형 우선 |
| 점프 | 중~상 | 입력 버퍼, 코요테 타임, 가변 점프 높이 |
| 공격 | 중 | 선·후딜, 판정 시점, 타격 정지와 피드백 |
| 적 AI | 중 | 2종의 상태 전환과 화면 밖 동작 제한 |
| 충돌 | 상 | 피격 판정, 지형 끼임, 연속 피격 방지 |
| 카메라 | 중 | 전방 시야, 경계 처리, 모바일 화면비 |
| 무기 | 중 | 기본 공격과 일시 강화의 공통 처리 |
| 보스 | 중~상 | 패턴 상태 관리, 예고와 판정 동기화 |
| 모바일 입력 | 상 | 동시 입력, 손가락 이탈, 입력 유예, 화면 크기 |

기술 난이도는 콘텐츠 양보다 입력과 충돌을 일관되게 느끼게 만드는 작업에 집중된다.

### 엔진 후보

| 기준 | Unity | Godot |
|---|---|---|
| 모바일 빌드 | Android / iOS 공식 빌드 체계와 관련 도구가 갖춰짐 | Android / iOS 내보내기를 공식 지원 |
| 2D 개발 | 범용 2D 물리·애니메이션·Tilemap 도구가 풍부함 | 2D 중심 노드와 장면 구조가 단순한 프로토타입에 적합 |
| AI / Codex 작업 | C#의 명시적 타입과 넓은 예제 기반이 유리 | GDScript와 텍스트 기반 구조가 짧은 반복 작업에 유리 |
| Asset Pipeline | 장기 확장과 외부 도구 연동 선택지가 많음 | 이번 스프라이트·애니메이션 범위에는 충분하고 가벼움 |
| 디버깅 | 성숙한 도구가 있으나 프로젝트 구성이 상대적으로 큼 | 실행 반복이 빠르나 출시 SDK 연동은 후속 검증 필요 |
| 기존 경험 | Unity / C# 경험이 있다면 큰 이점 | Godot / GDScript 경험이 없다면 초기 학습 필요 |
| 향후 확장 | 모바일 서비스와 상용 도구 연동에 유리 | 소규모 자체 구현에 적합하며 출시 요구 증가 시 재평가 |

**클라이언트 검토 결과:** 첫 프로토타입에 Godot와 GDScript를 권고했으며, 스튜디오 디렉터가 이를 승인했다. Project Knight의 엔진 및 기본 스크립트 언어는 `DEC-001`에 따라 Godot + GDScript로 확정한다.

Godot 공식 문서는 Android와 iOS 내보내기를 지원하지만 C# 모바일 내보내기는 실험적 제한이 있다고 안내한다. 따라서 Godot 선택 시 GDScript를 권장한다. Unity도 Android 빌드 지원 모듈과 SDK·NDK·JDK를 사용하는 공식 모바일 빌드 체계를 제공한다.

참고 자료(2026-09-05 확인):

- [Unity Android 환경 설정](https://docs.unity3d.com/6000.1/Documentation/Manual/android-sdksetup.html)
- [Unity iOS 빌드 및 배포](https://docs.unity3d.com/jp/current/Manual/ios-building-and-delivering.html)
- [Godot Android 내보내기](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_android.html)
- [Godot iOS 내보내기](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_ios.html)

엔진 결정은 Project Knight에만 적용하며 다른 프로젝트의 기본 엔진 정책으로 확대하지 않는다.

### 기술 위험요소

- 터치 동시 입력과 손가락 이탈로 핵심 조작이 누락될 수 있다.
- 애니메이션 선·후딜이 입력 지연처럼 느껴질 수 있다.
- 지형 경계·벽 처리에서 조작 일관성이 깨질 수 있다.
- 화면비에 따라 행동 버튼과 게임 시야가 겹칠 수 있다.
- 임시 표현(Placeholder)의 피드백 부족으로 실제 조작감보다 나쁘게 평가될 수 있다.

초기 구현에서는 단순 지형, 고정 물리 시간, 입력 버퍼, 코요테 타임, 피격 후 짧은 무적시간을 검증 항목으로 둔다.

## 4. 서버 리드 의견

| 기능 | 현재 필요 여부 | 판단 |
|---|---|---|
| 계정 | 불필요 | 단일 기기 프로토타입에 사용자 식별 불필요 |
| 로그인 | 불필요 | 계정 기능이 없음 |
| 저장 | 로컬만 필요 | 설정과 체크포인트는 기기 로컬 저장으로 충분 |
| 랭킹 | 불필요 | 경쟁 지표가 핵심 검증 질문이 아님 |
| 분석(Analytics) | 서버 불필요 | 초기 테스트는 관찰 기록과 간단한 로컬 로그로 충분 |
| 결제 | 불필요 | BM을 확정하거나 검증하는 단계가 아님 |
| 클라우드 저장(Cloud Save) | 불필요 | 장기 진행과 다중 기기 연속성이 없음 |

**서버 결론: 현재는 불필요하지만 이후 필요할 수 있다.**

프로토타입에는 Backend, 계정, 원격 Database, 서버 Analytics를 구축하지 않는다. 외부 테스트에서 사용자 지표나 원격 설정이 필요해질 때 다시 판단한다.

## 5. 사업 / 서비스 리드 의견

### 예상 사용자

- 고전 횡스크롤 액션의 패턴 학습과 재도전을 좋아하는 사용자
- 짧은 세션에서도 조작 숙련과 보스 돌파의 성취를 원하는 사용자
- 복고 표현보다 명확한 규칙과 손맛 있는 2D 액션을 찾는 사용자

시장 규모나 수익성을 주장하지 않고 플레이테스트 대상 가설로만 사용한다.

### 모바일 적합성

장점:

- 5~10분의 짧은 구간과 빠른 재도전은 모바일 세션에 맞출 수 있다.
- 단순한 횡스크롤 공간은 작은 화면에서도 목표를 전달하기 쉽다.
- 패턴 학습과 기록 개선은 반복 플레이 동기가 될 수 있다.

약점:

- 물리 버튼이 없어 정밀한 동시 입력과 빠른 방향 전환이 어렵다.
- 손가락이 적과 위험 신호를 가릴 수 있다.
- 높은 실패 빈도는 짧은 모바일 세션에서 이탈로 이어질 수 있다.

### 시장 차별화

- “어려운 복고 게임”보다 짧고 읽기 쉬운 전투 구간을 강조한다.
- 원작 외형이 아니라 공격 예고, 회피, 타격 반응이 만드는 현대적 조작 감각으로 차별화한다.
- 고유 실루엣과 움직임 규칙으로 단순 복고 복제(Retro Clone) 인상을 피한다.

### BM

프로토타입에서는 IAP, 광고, 배틀패스를 구현하거나 확정하지 않는다. 재미와 조작 적합성에 집중하고, BM은 반복 플레이 의향과 세션 구조가 확인된 뒤 검토한다.

### 프로토타입에서 확인할 시장성 질문

- 터치 조작으로도 실패 원인을 이해하고 다시 플레이하고 싶은가?
- 고전 액션의 긴장감이 불편함보다 성취감으로 느껴지는가?
- 5~10분 플레이 후 한 번 더 도전할 이유가 있는가?
- 임시 표현만으로도 독자적인 시각 방향의 가능성이 보이는가?

## 6. 스튜디오 매니저 종합안

### A. 프로토타입 목적

1. 터치 환경에서 이동·점프·공격·회피가 의도대로 연결되는가?
2. 읽을 수 있는 적 패턴과 빠른 재도전이 공정한 긴장감을 만드는가?
3. 5~10분 구간을 끝낸 뒤 다시 플레이하고 싶은가?

### B. 권장 핵심 플레이 루프

위험을 관찰하고 공격·이동·점프·회피를 선택해 짧게 실행한다. 실패하면 중간 체크포인트에서 빠르게 재도전하고, 학습한 패턴을 보스에서 종합적으로 사용한다.

### C. 권장 모바일 조작

**권장:** 왼쪽 넓은 수평 이동 영역과 오른쪽 공격·점프·회피 버튼. 공격 타이밍을 직접 선택해야 핵심 재미를 검증할 수 있다.

**대안:** 버튼 과밀이 심하면 좌우·공격·점프 버튼을 유지하고 회피는 이동 방향 두 번 입력으로 시험한다. 자동 공격은 우선 사용하지 않는다.

### D. 프로토타입 포함 범위

- 5~10분 분량의 선형 스테이지 1개
- 플레이어 1종과 이동·점프·공격·회피·피격
- 기본 무기 1종과 일시적 공격 강화 1종
- 행동이 다른 일반 적 2종과 재사용 강화형 1종
- 2~3개 패턴의 간단한 보스 1종
- 체력 3회, 중간 체크포인트 1개, 빠른 재시작
- 모바일 터치 UI와 최소 타격·피격·위험 예고

### E. 프로토타입 제외 범위

- 다중 스테이지, 분기, 메타 성장, 인벤토리
- 다수 캐릭터와 다수 무기
- 계정, 로그인, 서버, 랭킹, Cloud Save
- IAP, 광고, 배틀패스
- 최종 세계관·캐릭터·아트 스타일
- 최종 밸런스, 라이브 운영, 스토어 출시 기능

### F. 권장 아트 제작 방식

제한된 프레임의 2D 고해상도 스프라이트를 권고한다. 임시 Asset을 허용하되 플레이어 상태, 적 공격 예고, 피격 반응, 충돌 지형은 읽을 수 있어야 한다. 최종 아트 스타일은 확정하지 않는다.

### G. 기술 권고안

**결정:** Godot + GDScript

소규모 2D 프로토타입의 빠른 반복, 단순한 구조, AI Agent 중심 개발 검증을 우선한 선택이다. 스튜디오 디렉터가 승인했으며 상세 내용은 `DEC-001`을 따른다.

### H. 서버 권고안

현재 프로토타입에는 서버가 필요하지 않다. 저장은 로컬로 제한하고 Analytics는 플레이테스트 관찰과 선택적 로컬 로그로 대체한다. 외부 테스트 준비 시 재검토한다.

### I. 사업 / 시장 관점

BM이 아니라 터치 조작 후 재도전 의향, 실패의 공정성, 짧은 세션의 반복성, 오리지널 시각 방향의 가능성을 확인한다. 시장 수치나 수익 모델은 확정하지 않는다.

### J. 주요 위험요소

1. 터치 동시 입력과 화면 가림으로 핵심 조작이 불편할 수 있다.
2. 난이도가 패턴 학습보다 입력 실패로 느껴질 수 있다.
3. 조작감 개선보다 콘텐츠와 Art 범위가 먼저 커질 수 있다.
4. 임시 피드백 부족으로 전투 가능성을 낮게 평가할 수 있다.
5. 레퍼런스 외형을 따라 오리지널 IP 차별성이 약해질 수 있다.

### K. 스튜디오 디렉터 결정 필요사항

1. **조작:** 수평 이동 영역 + 공격·점프·회피 버튼 권고 / 회피 이중 입력 대안
2. **난이도:** 체력 3회, 중간 체크포인트, 빠른 재도전을 사용하는 중간 난이도 권고
